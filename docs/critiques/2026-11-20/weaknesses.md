## Weakness: Builder Capsule Clearance Returns the Farthest Sample, Not the Nearest

### Summary of Concern

`ClubSDF.signed_distance_capsule` is documented as the "minimum signed
distance from a capsule solid to the club grip", but it keeps the **maximum**
over the sampled centre points. Every builder non-penetration gate tests that
value against `-pad_tol`, so a finger or thumb segment whose interior sinks
into the grip still passes whenever one end is outside the grip.

### Location

- **File/Document:** `src/shared/python/grip_build/club_sdf.py`
- **Section:** `ClubSDF.signed_distance_capsule` (lines 40–61)
- **Claim or Equation:** `best = -math.inf` … `best = max(best, d)`; consumed
  as a penetration gate in `builder.py:170,188`,
  `stages_gb3.py:74,124,141,190` and `full_builder.py:191–200`

### Nature of the Issue

- [x] Logical gap
- [ ] Unstated assumption
- [ ] Overgeneralization
- [x] Empirical insufficiency
- [ ] Terminological ambiguity
- [ ] Literature conflict

### Why This Is a Problem

A phalanx wrapped around a cylinder is a chord. A chord touching the grip at
both ends has its midpoint *inside* the grip, so the true minimum clearance
there is negative while the endpoint samples read about zero. With `max`, the
gate reports "touching, OK" for the penetrating case. The same holds for the
bisection in `builder.py`: it can close a joint past first contact, because
the clearance it watches is set by the segment end that is farthest from the
grip. The committed `grip_builder_goldens.json` is generated by the same
function (`scripts/generate_grip_builder_goldens.py`), so the goldens fix the
behaviour in place rather than check it. The capsule-to-capsule path
(`geometry.capsule_capsule_signed_distance`) uses true closest points, so
finger-to-finger clearance and finger-to-club clearance are measured
differently.

A reviewer can therefore say that the builder's "contact without
penetration" receipts do not show non-penetration of the curled hand.

### Evidence / References

- Inline read of `club_sdf.py:55–61` together with the docstring at line 48.
- `grip_build/geometry.py:68–71` (min-distance semantics for the
  capsule-to-capsule case).

### Severity

- [ ] Low (clarification needed)
- [ ] Medium (argument tightening required)
- [x] High (core claim at risk)

### Suggested Remedies

- Add a failing test first: a capsule whose midpoint lies inside the grip and
  whose endpoints lie on or outside it must give a negative clearance.
- Use the minimum, or better an analytic segment-to-tapered-cylinder distance,
  so the result does not depend on `samples=12`.
- Regenerate the goldens and report how many stages change status from `OK`
  to `GAP` or penetration.
- Say in the receipt whether butt-cap distance is modelled. The point SDF is
  `hypot(x, y) - r(z)` with no axial end, so a segment past the butt still
  measures against an infinite cylinder.

## Weakness: Estimated Pad Shear Drops the Axial Pull That Causes Fly-Off

### Summary of Concern

When a contact run has no per-pad tangential channel, `grip_loss_loads`
estimates pad shear from the hand-on-club force. It projects out the
component **along the shaft axis** and keeps only the transverse part. On a
cylindrical pad the axial direction is tangential to the contact surface, so
the axial pull is exactly the shear that slides the club out of the hands.

### Location

- **File/Document:** `src/shared/python/grip_contact/grip_loss_loads.py`
- **Section:** `_estimate_tangential_from_hand_wrench` (lines 110–136)
- **Claim or Equation:** `transverse = force - axial`; shear allocated as
  `|transverse| · f_n / Σ f_n`

### Nature of the Issue

- [x] Logical gap
- [x] Unstated assumption
- [ ] Overgeneralization
- [ ] Empirical insufficiency
- [ ] Terminological ambiguity
- [ ] Literature conflict

### Why This Is a Problem

Late in the downswing the dominant hand-club load is the centripetal pull
along the shaft, which peaks at several hundred newtons for a driver. In a
radial-pad model, the transverse part of the hand force is carried largely by
pad *normal* reaction, not shear. So this estimate puts the wrong component in
the shear slot: it leaves out the axial shear and counts radial load as shear.
It also has no term for torque about the grip axis, which drives roll slip
(the "face opens in the hands" failure). The roll-slip channel already exists
in `ContactRun.roll_slip_rad` but does not enter the margin. The allocation
`∝ f_n` also assumes every pad is equally close to sliding, which is the
assumption a slip predictor exists to test.

Whether the committed driver and iron-7 receipts used this path depends on
whether their `.contact.npz` files have `tangential_force_{L,R}_n`. The
receipt does not say, so a reader cannot tell which load model produced the
"no slip" result.

### Evidence / References

- Nesbit, S. M. (2005), "A three dimensional kinematic and kinetic study of the
  golf swing", *J. Sports Sci. Med.* 4(4):499–519 — hand-club force is
  dominated by the shaft-axial component near impact.
- The repository's own `GripKineticsSeries.force_on_club_n` can quantify the
  axial share directly; the receipt should report it.

### Severity

- [ ] Low (clarification needed)
- [ ] Medium (argument tightening required)
- [x] High (core claim at risk)

### Suggested Remedies

- Decompose shear into axial and circumferential parts in the pad's local
  frame. Include the hand's moment about the grip axis divided by the grip
  radius as circumferential shear.
- Record in `serialise_grip_loss_report` which load path produced the
  tangential forces (`recorded` or `estimated`).
- Fail closed, or mark the report `estimated`, when tangential channels are
  missing, rather than silently using the transverse proxy.

## Weakness: The Grip-Loss Null Result Is Close to Circular, and Its Sensitivity Sweep Is Degenerate

### Summary of Concern

The committed receipts report no slip and no release for driver and iron-7
across a 3×3 friction × squeeze sweep. That result tells us little, for three
reasons:

1. The loads come from a MuJoCo run (`mujoco_<club>_run.json`) whose own
   contact already used `friction_static = 0.9` and the ~1104 N per-hand
   squeeze. The evaluator then re-checks Coulomb feasibility with the same
   μ = 0.9. Forces produced by a solver that kept the club held at μ = 0.9 will
   mostly satisfy μ = 0.9 by construction.
2. `squeeze_scale` multiplies normal **and** tangential force by the same
   factor (`grip_loss_evaluator._scale_loads`). The margin is
   `1 − f_t / (μ f_n)`, which does not change under that scaling; only pads
   near the 1 N floor can change state. The squeeze axis of the sweep is
   therefore close to a no-op, and the 3×3 grid is in effect 3×1.
3. The report does not serialise the minimum margin or where it occurs, so a
   null result cannot be read as "how close to slip".

### Location

- **File/Document:** `src/shared/python/grip_contact/grip_loss_evaluator.py`
  (lines 90–100, 200–230, 233–256);
  `docs/development/full_body_models/evidence/grip_kinetics/grip_loss_prediction_{driver,iron7}.json`
- **Claim or Equation:** all nine sensitivity rows `first_slip_s: null`

### Nature of the Issue

- [x] Logical gap
- [x] Empirical insufficiency
- [ ] Unstated assumption
- [ ] Overgeneralization
- [ ] Terminological ambiguity
- [ ] Literature conflict

### Why This Is a Problem

A statistician would call this a self-consistency check presented as a
prediction. A reviewer can say the evaluator could not have predicted slip on
these inputs, so its null result is uninformative. The ±10 % friction range is
also narrow compared with the measured spread of skin-on-rubber friction,
which changes by a factor of two or more with moisture, glove use and normal
pressure. The MuJoCo run's `friction_dynamic = 0.7` is not used in the
evaluator.

The disclaimer string is accurate in saying "not a simulated fly-off". It does
not warn that the inputs were produced under the same friction law that is
being tested.

### Evidence / References

- Derler, S. & Gerhardt, L.-C. (2012), "Tribology of skin: review and analysis
  of experimental results for the friction coefficient of human skin",
  *Tribol. Lett.* 45:1–27 — μ for skin ranges from about 0.2 to above 2,
  strongly dependent on moisture.
- Previous critique 2026-10-23, Finding 1 (squeeze and pad parameters not
  calibrated) — this evaluator inherits that gap.

### Severity

- [ ] Low (clarification needed)
- [x] Medium (argument tightening required)
- [ ] High (core claim at risk)

### Suggested Remedies

- Scale **only** `f_n` for squeeze sensitivity, or recompute loads from a
  re-run at a lower squeeze; record which was done.
- Add a "minimum margin over the swing, patch, time" field and the friction at
  which first slip would occur (the break-even μ). That is the useful output of
  an offline evaluator.
- Widen the friction sweep to a literature-backed range (for example 0.4–1.2),
  and state that the input loads were generated at μ_s = 0.9.

## Weakness: Hysteresis Thresholds and Dwell Times Have No Stated Basis

### Summary of Concern

The state machine's numbers (`slip_enter 0.0`, `slip_exit 0.06`,
`release_enter −0.15`, 4 ms dwell) appear only as CLI arguments and test
defaults. No source, calibration or argument is given for them. The evaluator
also takes `dt` as the median sample interval, which is wrong if the run is
irregularly sampled.

### Location

- **File/Document:** `src/shared/python/grip_contact/grip_loss_config.py`;
  `tests/unit/grip_contact/test_grip_loss_evaluator.py:34–48`;
  `grip_loss_evaluator.py:115`
- **Claim or Equation:** `dt = float(np.median(np.diff(time_s)))`

### Nature of the Issue

- [x] Unstated assumption
- [ ] Logical gap
- [ ] Overgeneralization
- [ ] Empirical insufficiency
- [ ] Terminological ambiguity
- [ ] Literature conflict

### Why This Is a Problem

A margin below zero is Coulomb-infeasible by definition, so "release" at
−0.15 assumes something like 15 % overload held for 4 ms before the hand
loses the club. Nothing physical is cited for that. With 908 samples over a
swing, 4 ms is a small number of frames, so the dwell filter depends on the
sampling rate. A control theorist would want the thresholds tied to a
measurable quantity, such as a slip displacement or slip velocity, which
`ContactRun.axial_slip_m` and `roll_slip_rad` already record.

### Severity

- [x] Low (clarification needed)
- [ ] Medium (argument tightening required)
- [ ] High (core claim at risk)

### Suggested Remedies

- Document the basis for each threshold, or state that they are placeholders.
- Cross-check predicted slip onset against the recorded `axial_slip_m` and
  `roll_slip_rad` channels from the same run. That is a free internal
  validation.
- Integrate dwell over the actual per-sample `Δt` instead of the median.

## Weakness: "Neutral" Grip Defaults Encode One Golfer's Preference

### Summary of Concern

`grip_spec/defaults.py` defines the neutral lead and trail thumb azimuths
(22.5°, 45°) as one individual's targets. It keeps the legacy 40° cross angle
and 20° V-azimuths without citation. These values are then used as the shared
default for every engine.

### Location

- **File/Document:** `src/shared/python/grip_spec/defaults.py:14–23`

### Nature of the Issue

- [x] Overgeneralization
- [x] Terminological ambiguity
- [ ] Logical gap
- [ ] Unstated assumption
- [ ] Empirical insufficiency
- [ ] Literature conflict

### Why This Is a Problem

"Neutral" in coaching literature is a range that depends on hand size and the
player, not a point value. A biomechanist would object to presenting one
player's set-up as the population default, especially next to the HRG
"human-realistic" framing.

### Severity

- [x] Low (clarification needed)
- [ ] Medium (argument tightening required)
- [ ] High (core claim at risk)

### Suggested Remedies

- Rename to `reference_player` or a similar term, or document the population
  range and cite a source.
- Keep the value as a default, but make the provenance explicit in the
  GripSpec receipt.
