# Functional Test Matrix and Computer-Control Test Plan

## Purpose and scope

This is the repeatable, release-facing manual functional test plan for
UpstreamDrift. The **PyQt6 launcher and native PyQt6 tools are the primary
product under test**. The React/Tauri shell is a secondary parity surface: it
must be compared with verified PyQt6 behavior, but it cannot define the
expected product behavior while it remains behind the native launcher. The
plan is a complement to automated tests; it records what a user can actually
open, operate, and observe.

The source of truth for the inventory is `src/config/models.yaml`,
`ui/src/App.tsx`, and `SPEC.md`. Items marked `experimental`, `beta`, or
`deprecated` are tested for honest and safe behavior; they are not held to the
same release bar as `ready` features. Optional engines and third-party tools
may be recorded as **blocked by an unavailable dependency**, never as passed.

## Test execution rules

1. Start with a clean product process set and record the commit SHA, OS,
   product build, backend URL, and installed optional dependencies.
2. Use only disposable fixture data. Do not upload real participant data or
   credentials. Create outputs in a per-run temporary workspace.
3. Record one result per matrix ID: `PASS`, `FAIL`, `BLOCKED`, or `NOT RUN`.
   A pass needs the stated observable result; opening a screen alone is not a
   pass for an action.
4. On failure, capture the exact repro steps, expected/actual result, error
   text, screenshot, product/build information, and diagnostic logs. Check a
   second time from a clean state before filing, unless it crashes or risks
   data loss.
5. File each confirmed defect as a GitHub issue linked to the current
   functional-testing epic. Do not close a defect merely because it cannot be
   reproduced on a different optional-engine configuration.
6. Update the execution record in this document after every test campaign and
   link the epic and all newly filed defects. A release candidate cannot claim
   functional sign-off while any `ready` critical-path item is failed or not
   run without an explicit waiver.
7. Execute `QT-*` and native-tool rows before `WEB-*`. For every relevant
   React/Tauri observation, identify the equivalent PyQt6 workflow and record
   it as `parity`, `gap`, or `not comparable`; a web-only limitation is a
   product-parity gap, not a reason to weaken the PyQt6 expectation.

## Computer-control agent script

1. Capture the baseline: build/commit/dependencies, PyQt6 launcher screenshot,
   backend logs location, and matrix IDs assigned to the run.
2. Execute all preflight rows. If PF-01 fails, file a P0 issue and continue
   only with directly launchable product surfaces.
3. Work P0 rows first in the order `SH` → `QT` → `ENG`/`SIM` → `REL`.
   Begin `WEB-*` only as a parity comparison after the matching PyQt6 evidence
   exists.
   For each row, observe before acting and after each state-changing action.
4. Treat an optional dependency as blocked only after the product's own
   diagnostic/probe or a direct launch demonstrates its absence. A present
   dependency that crashes, hangs, or yields a false success is a failure.
5. On a suspected defect, reproduce once from a clean screen/process state.
   Capture the matrix ID, deterministic steps, expected versus actual result,
   screenshot, log path, build/commit, and dependency status.
6. Create one issue per independently actionable defect. Add it to the current
   testing epic in the issue body and update the epic's checklist. Do not use
   production/sensitive data, install software, change permissions, or submit
   external communications outside the GitHub issues explicitly authorized for
   this campaign.
7. Mark every attempted row in the execution record. End with: totals by
   result and priority, issue links, blockers, and the exact next matrix slice.

## GitHub issue templates

### Epic

`[Epic] Functional product testing — <release/build>`

Body sections: scope and build, acceptance criteria, matrix document link,
execution checklist grouped by matrix area, confirmed-defect checklist,
blocked dependency checklist, and sign-off criteria.

### Defect

`[Functional QA][<matrix ID>] <concise observed failure>`

Body sections: environment/build, matrix ID, preconditions/fixture,
reproduction steps, expected result, actual result, evidence (screenshots/log
path), reproducibility, impact/severity, and `Parent epic: #<number>`.
