# Option 3 — Assumptions

> Read these before writing code. If any of them break, the option breaks.

## A1. Under-determination is the central problem

When only the club is observed, the joint torques that produce a given club trajectory are **not unique**. There is an entire manifold of coefficient vectors `{θ : sim(θ) ≈ q_meas}` for any given target. A deterministic regressor `g_φ : x → θ` trained with MSE on this dataset would output the **mean of the manifold**, which is generally not on the manifold — it is an unphysical "average swing" that does **not** reproduce the target when round-tripped through Simscape.

This is why Option 3 is a CVAE, not a feedforward MLP. The latent `z` is what disambiguates which point on the manifold to pick.

## A2. The latent prior is what disambiguates

The CVAE latent `z` is constrained to be likely under a prior `p(z) = N(0, I)`. During training, the KL term forces the per-target posteriors `q(z | x_i)` toward the prior, which means at inference `z ~ N(0, I)` samples cover the manifold. The choice of prior is the **inductive bias** that says "all swings on the manifold are a priori equally likely." We bend this toward physiologically plausible swings via two mechanisms:

1. **Implicit bias from the dataset.** The random-sweep parquet was generated by sampling coefficients within physically reasonable bounds and running them through Simscape. The dataset's coefficient distribution is the **implicit prior over swings** that the model learns. If the dataset over-represents high-effort swings, the CVAE will too.
2. **Explicit work regularizer.** During training we add a term `λ_W · |Ŵ(θ̂) − W_trial|` where `W_trial` is the dataset's logged `total_work_J` for the trial. This nudges the decoder toward picking modes whose total work matches the demonstration. At inference, we can downweight `z` samples that decode to high-work coefficients (rejection sampling on work, not just RMSE).

If either of these breaks — sparse dataset, biased dataset, or the regularizer is too weak — the latent prior is doing nothing useful and `g_φ` reverts to averaging.

## A3. The dataset's coefficient distribution is the de facto prior over swings

We have **no prior over real human swings yet** (no large mocap corpus). The random-sweep dataset is a synthetic uniform-ish prior over what the model **can** produce. This is fine for the model's basin of validity but means:

- A real human swing whose coefficient vector lies far outside the random-sweep support **will not be fit well** by Option 3. The CVAE has never seen that mode and will hallucinate.
- The "minimum-work" bias is therefore relative to the dataset's work distribution, not relative to truth.

When real-mocap data accrues, retrain. Until then, **always validate on synthetic-from-known-coefficients targets** to keep the failure mode visible.

## A4. Without round-trip validation, predictions are unsafe

A single `g_φ(x)` forward pass returns **one sample** from the posterior. There is no guarantee it is the right sample. Round-tripping through Simscape and measuring the actual club RMSE is the **only** honest measure of whether the prediction works. Pipeline rule:

> Never ship a `g_φ` output to a downstream consumer (replay, optimizer, RL critic, leaderboard) without round-trip validation. Doing so will eventually produce a confident-looking, completely wrong fit.

Rejection sampling budget is documented in [APPROACH.md §Inference](APPROACH.md#inference); the default is up to 32 samples per target and accept the lowest round-trip RMSE.

## A5. Mode collapse is the dominant failure mode

CVAEs have a known pathology: the encoder learns to ignore `z` entirely and the decoder becomes deterministic (`q(z|x) → δ(z)` and the KL term goes to zero). When this happens, Option 3 silently regresses to a deterministic regressor and inherits all the under-determination problems from §A1.

We defend with three things:

1. **KL annealing schedule** — start with KL weight `β = 0`, ramp to `β = 1` over the first 20 epochs.
2. **`test_kl_does_not_collapse`** — held-out batch must show `KL > 0.5 nats`. Fails the build if not.
3. **`test_multiple_samples_produce_distinct_coefficients_for_under_determined_target`** — coefficient stddev across samples must exceed a noise floor.

If a model passes training-loss but fails these tests, **it is broken** even if the loss curve looks healthy.

## A6. Training compute and dataset size

We assume:

- The random-sweep dataset has `≥ 10k` trials and `≥ 20k` is preferred.
- Training fits on a single workstation GPU (12+ GB VRAM) in `< 8 hours`. If not, drop the encoder dimension or sub-sample trials. Do not silently move to multi-GPU without flagging it in the issue.
- A held-out test split of `≥ 10%` is reserved for round-trip validation and never seen during training.

## A7. Simulation timegrid is fixed and matches the dataset

Per [shared/COST_FUNCTION_SPEC.md §Defaults](../shared/COST_FUNCTION_SPEC.md#defaults), `sample_rate = 1000 Hz` and simulation duration `≈ 0.3 s`. The dataset is assumed to be sampled at this rate. If the dataset was generated at a different rate, **resample at load time** in the shared loader, not in this folder. We do not handle variable-length sequences in v1.

## A8. The CVAE encoder consumes the canonical `ClubTarget` schema

Encoder input is the [CLUB_IK_SPEC.md](../shared/CLUB_IK_SPEC.md) `ClubTarget` schema: `(time, butt, clubhead, club_quat, impact_idx)`. Anything else (raw mocap, body markers, EMG) is out of scope for v1. Phase 2 may extend it; see [APPROACH.md §Future work](APPROACH.md#future-work).

## A9. Decoder output is `n_joints × 7` flat coefficient vector

Decoder output matches the decision-variable definition in [shared/README.md §Hard constraints](../shared/README.md#hard-constraints-assumptions-all-four-options-must-respect). Bounds (A,B ∈ ±1000; C,D ∈ ±500; E,F ∈ ±100; G ∈ ±25) are enforced by **scaled tanh activation** at the output, not by a clip. This is differentiable for joint training and prevents the decoder from outputting infeasible coefficients.

## A10. Identical numerics with the rest of the pipeline

The cost function used to score an Option 3 fit is **byte-identical** to the one Options 1, 2, and 4 use — see [shared/COST_FUNCTION_SPEC.md](../shared/COST_FUNCTION_SPEC.md). The Python implementation under `src/shared/python/motion_matching/cost.py` is the canonical scorer. Never reimplement the cost function inside this folder.
