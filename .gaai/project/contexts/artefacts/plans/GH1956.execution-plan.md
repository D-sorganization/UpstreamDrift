# Execution Plan: GH1956 — Consolidate GUI Interfaces and ensure strict lazy-loading of engine dependencies

## Summary

Three dashboard launcher files in `src/launchers/` import heavy engine-specific physics engine classes at the top-level (module scope). When any of these files is imported (e.g., by the registry scanning all launcher files), the entire physics engine dependency chain is triggered unconditionally — even if the user never activates that engine tab.

The fix is straightforward: convert the top-level physics engine imports in each dashboard file into deferred (lazy) imports inside their `main()` function body.

No architectural changes are required. The established pattern already exists in the codebase (`launcher_constants.py` provides `_lazy_load_engine_manager()`, `_lazy_load_model_registry()` as precedents). The approach here is simpler: move the import statement to the point-of-use (inside `main()`).

## Implementation Sequence

### Step 1: Fix `mujoco_dashboard.py`

Remove the top-level import:

```python
from src.engines.physics_engines.mujoco.python.mujoco_humanoid_golf.physics_engine import (
    MuJoCoPhysicsEngine,
)
```

Move it inside `main()`:

```python
def main() -> None:
    from src.engines.physics_engines.mujoco.python.mujoco_humanoid_golf.physics_engine import (
        MuJoCoPhysicsEngine,
    )
    launch_dashboard(
        engine_class=MuJoCoPhysicsEngine,
        title="MuJoCo Golf Analysis Dashboard (Unified)",
    )
```

### Step 2: Fix `pinocchio_dashboard.py`

Remove the top-level import:

```python
from src.engines.physics_engines.pinocchio.python.pinocchio_physics_engine import (
    PinocchioPhysicsEngine,
)
```

Move it inside `main()`.

### Step 3: Fix `drake_dashboard.py`

Remove the top-level import:

```python
from src.engines.physics_engines.drake.python.drake_physics_engine import (
    DrakePhysicsEngine,
)
```

Move it inside `main()`.

### Step 4: Write tests

Create `tests/unit/test_launcher_lazy_loading.py` with:

1. `test_mujoco_dashboard_no_engine_import_at_module_level` — mock the mujoco physics engine module, import `mujoco_dashboard`, verify the mock was NOT called.
2. `test_pinocchio_dashboard_no_engine_import_at_module_level` — same for pinocchio.
3. `test_drake_dashboard_no_engine_import_at_module_level` — same for drake.
4. `test_mujoco_dashboard_importable_without_mujoco_installed` — patch the engine module as unavailable at import time, confirm module-level import succeeds (lazy behavior).
5. `test_pinocchio_dashboard_importable_without_pinocchio_installed` — same for pinocchio.
6. `test_drake_dashboard_importable_without_drake_installed` — same for drake.

## Edge Cases

- `drake_dashboard.py` also imports `QFileDialog` at module level — that is a PyQt6 import (not a physics engine), so it stays (PyQt6 is a required GUI dep, not an optional heavy engine dep).
- `launch_dashboard` from `src.shared.python.dashboard.launcher` stays at module level in all three files — it is already a shared utility, not an engine import.
- No changes to any test files that currently test these modules at a higher level (they mock entire modules anyway).
